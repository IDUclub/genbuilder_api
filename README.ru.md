# GenBuilder API
API для GenBuilder. Генерирует изображения кварталов со зданиями и другими объектами, векторизует и нормализует их.

## 3D-фасады (задачи facade-jobs)

Асинхронным 3D-эндпоинтам нужен отдельный деплой `facade-jobs`:

| Переменная окружения | Обязательна | По умолчанию | Назначение |
|---|---:|---:|---|
| `FACADE_JOBS_API` | да | — | Внутренний базовый URL, которым пользуется GenBuilder, например `http://facade-jobs:8000` |
| `FACADE_JOBS_PUBLIC_API` | нет | `FACADE_JOBS_API` | Публичный базовый URL для возвращаемого `status_url` |
| `FACADE_JOBS_TIMEOUT_SECONDS` | нет | `30` | Таймаут постановки в очередь; время генерации фасадов он не покрывает |

Контракты эндпоинтов и сервиса описаны в [руководстве по API для фронтенда](docs/frontend-api-guide.md#3d-фасады)
и в [плане интеграции](docs/facades-3d-integration-plan.md).

Все эндпоинты `/generate/3d/*` принимают необязательное русское название пресета
или английский промпт в query-параметре `facade_style`. `/generate/chat/stream/3d`
принимает то же значение multipart-полем и умеет извлекать произвольные русские
описания из `user_query`. Без стиля для каждой функциональной зоны берётся её
пресет по умолчанию.

Чат-стрим собирает стили-пресеты из библиотеки фасадов и перед `done` отдаёт
событие `facade_scene` с готовой сценой. Если задан `FACADE_JOBS_API`, а в библиотеке
нужного нет или стиль задан свободным текстом, чат переходит на событие `facade_job`;
без facade-jobs чат работает только с библиотекой.

### Библиотека фасадов

Встроенные стили можно собирать и синхронно — из заранее сгенерированных секций
фасадов, хранящихся в MinIO под `FACADE_LIBRARY_PREFIX`. У каждого стиля по три
варианта (seed) на каждую ширину (6, 9, 12, 18, 24 м); каждый сгенерирован как стена
в 8 этажей и 32 м, потому что Facades-3D рисует один этаж примерно на 4 м высоты стены.
Секция режется на первый, типовой и верхний этажи, и каждая стена набирается из них
до реальной этажности здания; стены шире 24 м делятся на равные сегменты. Здание
выбирает один вариант по хешу своего id, поэтому все его стены совпадают, а соседние
здания различаются. `facade-jobs` по-прежнему читает старую раскладку `facade-library/v1`.
Query-параметр `facade_source` у `/generate/3d/*` выбирает `gpu` (поставить задачу, `202`),
`library` (собрать сразу, `200`, при промахе — ближайшая ширина) или `library_then_gpu`
(библиотека, если для каждой стены есть секция, иначе задача). Сцены из библиотеки
отдаёт `GET /facade-scenes/{result_id}.glb`; превью стилей — `GET /facade-styles` и
`GET /facade-styles/{style_id}/preview.glb`.

| Переменная окружения | По умолчанию | Назначение |
|---|---:|---|
| `FACADE_SOURCE_DEFAULT` | `gpu` | Источник, если `facade_source` не передан |
| `FACADE_LIBRARY_PREFIX` | `facade-library/v2` | Префикс объектов: манифест библиотеки, секции и превью |
| `FACADE_LIBRARY_PPM` | `32` | Разрешение текстур используемых секций |
| `FACADE_LIBRARY_MAX_WIDTH_SCALE` | `2.5` | Максимальное растяжение секции по горизонтали |
| `FACADE_LIBRARY_MAX_WALLS` | `5000` | Сцены крупнее уходят в `facade-jobs` (или `413`, если его нет) |
| `FACADE_LIBRARY_MANIFEST_TTL_SECONDS` | `300` | Сколько кешируются манифест и индекс превью |

Библиотеку и превью наполняет
[`scripts/build_facade_library.py`](scripts/build_facade_library.py) с машины, у которой
есть доступ и к MinIO, и к GPU-хосту Facades-3D (VPN). Скрипт читает переменные
`FILESERVER_*` и игнорирует локальный HTTP-прокси:

```bash
python scripts/build_facade_library.py check
python scripts/build_facade_library.py prewarm --dry-run
python scripts/build_facade_library.py prewarm --styles brick glass
python scripts/build_facade_library.py previews
```

`prewarm` генерирует `--variants` секций (по умолчанию 3) на каждый стиль и ширину
(`--section-floors` и `--section-floor-height`, по умолчанию 8 × 4 м), пропускает уже
существующие секции (`--force` генерирует их заново) и переписывает манифест после
каждой секции, поэтому его можно прервать и продолжить. `previews` набирает 3, 6 и 12
этажей из секции варианта 0 шириной 12 м каждого стиля в низкий, средний и высокий
боксы превью.

## Конфигурация

Для чата через vLLM задайте `VLLM_BASE_URL` — адрес сервера и `CHAT_MODEL` — точный
идентификатор модели из `/v1/models` (например, `qwen3.8-27b`). По умолчанию запросы
отключают thinking через `chat_template_kwargs: {"enable_thinking": false}`; прежний
неявный `reasoning_effort=low` больше не отправляется. Явно переданный
`reasoning_effort` по-прежнему имеет приоритет для вызовов, которым нужны рассуждения.

При переходе с GPT-OSS на Qwen3.8-27B отдельно управляемый сервер vLLM нужно
запустить с `--reasoning-parser qwen3`, как описано в
[рецепте vLLM для Qwen3.8-27B](https://recipes.vllm.ai/Qwen/Qwen3.8-27B).

Общая матрица приоритетов совпадает с PzzCompareAPI:

| Операция LLM | Категория | Переменная окружения | По умолчанию |
|---|---|---|---:|
| Извлечение параметров, определение атрибутов зон и маппинг | live-long / blocking | `VLLM_REQUEST_PRIORITY` | `-60` |
| Заголовок нового чата | live / semi-blocking | `VLLM_REQUEST_PRIORITY` | `-60` |
| Итоговое резюме для пользователя | live / blocking | `VLLM_CHAT_PRIORITY` | `-100` |

Каждый запрос, включая повторы, передаёт `priority` в JSON-теле. Обе настройки
принимают знаковые 64-битные целые; `0` отключает приоритизацию. Ненулевые значения
требуют запуска сервера vLLM с `--scheduling-policy priority`; планировщик по умолчанию
`fcfs` их отклоняет. Меньшие числа обрабатываются раньше.
См. [документацию планировщика vLLM](https://docs.vllm.ai/en/latest/cli/serve/#scheduling-policy).

Workflow деплоя может собирать `.env.development` прямо из настроек репозитория
на GitHub (`Settings` → `Secrets and variables` → `Actions`):

- переменная `ENV_APP` — нечувствительные параметры приложения;
- переменная `ENV_URLS` — URL сервисов, хосты и порты;
- секрет `ENV_SECRET` — учётные данные и `ADMIN_API_TOKEN`.

Каждое значение — многострочный фрагмент dotenv. Они склеиваются в этом порядке,
поэтому при дублировании ключа побеждает `ENV_SECRET`. `ENV_FILE` и `ENV_PATH`
остаются как устаревшие запасные варианты. Поддерживаемые ключи и рекомендуемая
группировка — в [`.env.example`](.env.example).

### API рантайм-конфигурации

Если задан `ADMIN_API_TOKEN`, действующие нечувствительные настройки можно менять
без пересборки и перезапуска контейнера. Токен передаётся в заголовке
`X-Admin-Token`:

- `GET /admin/config/settings` — типизированные действующие настройки (секреты замаскированы);
- `GET /admin/config/overrides` — активные постоянные оверрайды;
- `GET /admin/config/{key}` — действующее значение и статус оверрайда;
- `PUT /admin/config/{key}` с `{"value":"...","updated_by":"..."}` — проверить и задать;
- `DELETE /admin/config/{key}` — снять и вернуть значение из деплоя;
- `POST /admin/config/reload` — принудительно синхронизировать этот процесс.

Пример:

```bash
curl -X PUT http://localhost:8200/admin/config/VLLM_BASE_URL \
  -H 'X-Admin-Token: <ADMIN_API_TOKEN>' \
  -H 'Content-Type: application/json' \
  -d '{"value":"http://new-llm:8001","updated_by":"operator"}'
```

Оверрайды хранятся в SQLite по пути `RUNTIME_CONFIG_PATH` на постоянном томе Docker
`runtime_config` и синхронизируются каждым процессом (по умолчанию TTL 5 секунд).
Неизвестные ключи, учётные данные и boot-only настройки отклоняются.

## Сгенерированные геослои

Генерация в чате хранит свои артефакты (сгенерированные здания и, если пользователь
его загрузил, файл кварталов) в S3-совместимом объектном хранилище и отдаёт фронтенду
долговечные ссылки на них. Функциональные зоны **не** хранятся: они принадлежат
сценарию в UrbanDB и отдаются живым запросом, поэтому доступ проверяется заново при
каждом обращении.

| Переменная окружения | Обязательна | По умолчанию | Назначение |
|---|---:|---:|---|
| `FILESERVER_ENDPOINT` | да* | — | host:port S3 API MinIO, например `10.32.1.42:9000` |
| `FILESERVER_ACCESS_KEY` | да* | — | Ключ доступа с ограниченными правами |
| `FILESERVER_SECRET_KEY` | да* | — | Секретный ключ с ограниченными правами |
| `FILESERVER_BUCKET_NAME` | да* | — | Бакет со слоями, например `genbuilder` |
| `FILESERVER_SECURE` | нет | `true` | HTTPS к MinIO; `false` — только для endpoint на чистом HTTP |
| `FILESERVER_REGION` | нет | `us-east-1` | Передаётся явно, чтобы клиент никогда не вызывал `GetBucketLocation` — на это у ограниченных учётных данных нет права |
| `OUTPUTS_DIR` | нет | `outputs` | Локальный запасной каталог; используется, только если не задана ни одна переменная `FILESERVER_*` |
| `DEFAULT_SERVICES_TERRITORY_ID` | нет | `1` | Регион UrbanDB, чьи нормативы сервисов используются для размещения сервисов в чате без проекта, когда в запросе нет ни `territory_id`, ни `project_id`. `1` — Ленинградская область; пустое значение отключает запасной вариант |

\* Все четыре обязательны вместе. Неполный набор отклоняется при старте бэкенда
хранилища, а не молча подменяется локальным диском — иначе продовые ссылки сломались
бы при следующем перезапуске контейнера.

Бакет создаётся отдельно; у учётных данных нет права `CreateBucket`, и во время
работы ничего не создаётся.

**Срок хранения задаётся правилом бакета, а не кодом.** Установите на бакет
истечение через 30 дней, иначе сохранённые слои будут копиться бесконечно:

```bash
mc ilm rule add --expire-days 30 <alias>/genbuilder
```

Фронтенд должен считать `404` от `/files/{slot}/{result_id}` ожидаемым исходом при
чтении старого чата. См.
[руководство по API для фронтенда](docs/frontend-api-guide.md#5-геослои-подложка-и-ссылки-в-истории).

## Текстовые отчёты сервиса

После выполнения операции чат дополнительно возвращает событие `file` с
`name: "report"`, `role: "report"`, `mime_type: "text/plain"`, `filename: "Отчёт.txt"`.
Обычный текстовый ответ остаётся в потоке. Ссылка на отчёт сохраняется рядом с ним
в истории ChatStorage как часть `kind: "file"`; содержимое файла в историю не копируется.

Дескриптор содержит две долговечные ссылки относительно базы `source_service`:

- `url`: `GET /reports/id` — UTF-8 текст для просмотра (`Content-Disposition: inline`).
- `download_url`: тот же адрес с `?download=true` — скачивание (`attachment; filename="report.txt"`).

В SSE `event: file` поля дескриптора находятся непосредственно в JSON `data`.
Отчёт включает полный ответ, сводку застройки, целевые и достигнутые показатели по зонам, дефициты, параметры и замечания. Он формируется из результата генерации даже при сбое текстового резюме LLM.

Фронтенду следует читать отчёт как текст, не как GeoJSON и не как HTML. Для показа
достаточно `fetch(url).text()` и текстового компонента с сохранением переносов строк.
Ссылки проходят через API сервиса: доступ к внутреннему MinIO браузеру не нужен.
Запросы отчёта требуют тот же Bearer-токен, что и запросы слоёв. При сбое хранилища приходит `warning` с `stage: store_report`.


Отчёт оформлен на русском языке по образцу нормативной проверки: заголовки,
таблица сводных показателей и отдельные разделы подробностей. В отчётах ПЗЗ
объекты сгруппированы по соответствию и необходимости ручной проверки;
результат классификации не объявляется проверкой соответствия ПЗЗ.
Текст сохраняется в UTF-8 TXT с разметкой Markdown, пригодной для отображения
на фронте. Служебные поля API исключены; названия параметров, зон и системные
статусы переведены. Исходные коды зон, ВРИ, документов и значения показателей
сохраняются. Изменения касаются представления отчёта, схема JSON и SSE не меняется.

Для скачивания используется русское имя `Отчёт.txt` через параметр заголовка `filename*`; `filename` содержит совместимое резервное имя.
